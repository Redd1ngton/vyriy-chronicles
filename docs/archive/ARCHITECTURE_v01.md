# Вирій: Хроніки Оберегу — технічна специфікація v0.1

## 1. Продукт і межі реалізації

Мобільна соло Web RPG, натхненна структурою розвитку Ragnarok Online. Усі назви, сюжет, процедурна графіка та код у цьому проєкті оригінальні. Немає скопійованих RO-спрайтів, музики чи карт.

**Реалізовано:** 6 активних героїв, перемикання лідера, рух дотиком, пошук найкоротшого шляху, 3 тактики, автобій, навички, характеристики, Base/Job досвід, новачок і 18 наступних професій, інвентар, купівля, продаж луту, 2 слоти спорядження, карти, 40 істот, 5 регіонів, 5 сюжетних завдань, щоденне полювання, офлайн-розрахунок, локальне збереження та експорт/імпорт.

**Обмеження MVP:** не MMORPG; немає реальних інших гравців, P2P-торгівлі, гільдій, авторизації та серверного античиту. Піксельні портрети є тимчасовими; повноцінні мальовані аніме-портрети не включені. Є анімація спрайтів, ходьби, вогню, води й чисел шкоди, але немає повного набору намальованих покадрових бойових анімацій. Кожна професія має одну активну навичку з рангами; розгалужені багатонавичкові дерева, статуси, окремий радіус агресії, зброя за класами та складні бос-механіки потребують наступної ітерації. Характеристики специфічної поведінки істот у бестіарії частково є дизайном: зараз реально діють рівень, HP/ATK/DEF/FLEE, стихійний множник магії та атака боса по загону. MDEF і прискорення касту розраховано/специфіковано, але повного таймера касту та магічних атак ворогів ще немає.

## 2. Сюжет і цикл

Оберіг між Яв’ю та Нав’ю розколовся. Берегиня Орися доручає шістьом новачкам відновити п’ять осередків світла. На Вербових луках вони знайомляться з боєм; у Поліссі шукають голос старого дуба; на болотах повертають спокій потерчатам; у Карпатах знаходять вогонь горна; біля Брами Наві протистоять Чорнобогу.

Цикл: завдання → подорож → вибір цілі / автобій → здобич → характеристики й спорядження → професія → новий регіон. Провал бою повертає загін до табору без втрати луту. Це дружня до мобільного гравця модель MVP, а не точна емуляція RO.

| Регіон | Рівні | Істот | Бос |
|---|---:|---:|---|
| Вербові луки | 1–8 | 8 | Луговий вартовий |
| Шепіт Полісся | 9–20 | 8 | Дубовий страж |
| Болота Наві | 21–35 | 8 | Володар трясовини |
| Кам’яні Карпати | 36–55 | 8 | Дідо-велет |
| Брама Чорнобога | 56–80 | 8 | Чорнобог |

Зони відкриваються послідовним завершенням сюжетних завдань. Кожний регіон має окрему палітру, але у MVP вони використовують спільну геометрію карти. Рекомендований розвиток: полювання біля свого рівня, спорядження, збільшення VIT, зілля, зміна професії.

## 3. Архітектура клієнта

Без зовнішніх бібліотек та CDN. ES modules, Canvas 2D, CSS Grid, HTML dialog, localStorage. Статична директорія `dist` працює на звичайному HTTP-хостингу, зокрема Cloudflare Pages. Поточний застосунок не потребує сервера бази даних.

| Модуль | Обов’язок |
|---|---|
| `data.js` | Професії, предмети, істоти, регіони, сюжетні завдання |
| `engine.js` | Чисті формули, здобич, досвід, предмети, перехід професії, офлайн, pathfinding |
| `world.js` | Ізометрична проєкція, terrain, об’єкти, спрайти, камера, ефекти |
| `game.js` | Стан сесії, контролер бою/руху, меню, збереження, DOM |
| `style.css` | Десктоп, portrait і landscape, safe-area, модальні панелі |

Малювання — requestAnimationFrame; крок симуляції обмежений 60 мс для захисту від великих стрибків часу. При прихованій вкладці симуляція і малювання не виконуються; офлайн-винагорода розраховується один раз при поверненні. HTML-індикатори оновлюються приблизно 2,5 рази на секунду. Статичне поле 26×26 клітин. BFS дає найкоротший шлях при однаковій ціні переходів у 4 напрямках; діагональне зрізання кутів відсутнє. Для більших карт: A*, occupancy grid, web worker для маршрутизації та pooled rendering.

Герої й монстри малюються за глибиною `x+y`. Камера слідує за лідером з інтерполяцією. CSS image-rendering зберігає різкість пікселів. Поточний стиль — псевдоізометричний піксельний прототип, не повноцінний 3D HD-2D рушій.

## 4. База даних і модель даних

Повна референсна PostgreSQL DDL: `schema.sql`. Це цільова серверна схема, а не база, запущена у браузері.

Основні зв’язки:
- account → до 6 party_slots → heroes; один лідер.
- heroes → jobs; job_edges задає можливі переходи і потрібний Job Level.
- skills → skill_edges → hero_skills: багаторівневі передумови.
- inventory_instances → item_templates; equipment посилається на конкретні екземпляри.
- socketed_cards прив’язує карту до конкретного гнізда предмета.
- monsters → drop_table → item_templates.
- quest_progress має ключ періоду для щоденних/тижневих завдань.
- market_listings, wallets, ledger, idempotency забезпечують атомарну економіку.

На рівні сервісу перевіряти: власника героя/предмета, унікальність героя в загоні, доступність професії, максимум рангу навички, місткість гнізд, придатність карти, сумісність екіпіровки, кап HP/SP і рівнів. Самі зовнішні ключі не перевіряють однакового власника у пов’язаних таблицях — потрібна транзакційна перевірка сервісу або складені owner-aware FK.

Локальний JSON має `version:1`, heroes, inventory, wallet-поле zeny, quest, bounty, region, lastSeen, afkZone. Міграції наступних версій виконувати до запуску симуляції. JSON-експорт — резервна копія, а не доказ легітимного прогресу. У продакшні імпорт соло-збережень не переносить валюту на загальний ринок.

## 5. Герої та професії

Усі починають Base 1 / Job 1. Base рівень дає +3 очки характеристик; Job рівень — +1 очко навичок. Вартість характеристики у MVP постійна: 1 очко. Пороги: Base XP = `50 × поточний рівень`, Job XP = `35 × поточний рівень`. Усі шість отримують повний досвід за перемогу; це свідоме прискорення соло-загону. Капи: Base 99, Job 50.

На Job 10: Мечник, Маг, Лучник, Послушник, Торговець, Злодій. На Job 40 першої професії:

| Перша професія | Друга професія A | Друга професія B |
|---|---|---|
| Мечник | Лицар | Хрестоносець |
| Маг | Чарівник | Мудрець |
| Лучник | Мисливець | Бард / Танцівник |
| Послушник | Жрець | Монах |
| Торговець | Коваль | Алхімік |
| Злодій | Асасин | Розбійник |

Перехід скидає Job рівень/досвід/ранг активної навички, але зберігає Base рівень, характеристики та екіпіровку. Невитрачені очки старого Job у MVP скидаються: це зазначено як спрощення, у production потрібно зберігати окремі бюджети кожного tier і навички попередніх класів. Стать/вигляд не повинні блокувати вибір Bard/Dancer.

| Характеристика | Ефект |
|---|---|
| STR | ATK +2 за очко; вага +20 |
| AGI | ASPD +0,5; FLEE +1,4 |
| VIT | Max HP +12; DEF +1,2; HP regen +0,02/с |
| INT | MATK +3; Max SP +5; MDEF +1; SP regen +0,02/с |
| DEX | HIT +2; ASPD +0,15; у production — час касту й ranged ATK |
| LUK | CRIT +0,3 п.п.; perfect dodge +0,1 п.п.; карта +0,05 п.п. |

## 6. Бойові формули

Формули авторські, натхненні RO; вони не претендують на точну відповідність певному офіційному ruleset. Перевірені автоматичними тестами інваріантів.

```text
ATK = 8 + 2×Base + 2×STR + weapon.ATK + cardsBonus
MATK = 8 + Base + 3×INT + weapon.MATK + cardsBonus
MaxHP = 90 + 16×Base + 12×VIT
MaxSP = 25 + 2×Base + 5×INT
DEF = 1.2×VIT + armor.DEF
MDEF = INT + 0.3×VIT
HIT = 80 + Base + 2×DEX
FLEE = Base + 1.4×AGI
ASPD = clamp(150 + 0.5×AGI + 0.15×DEX, 150, 190)
attackIntervalSeconds = 0.04 × (200−ASPD)
hitProbability = clamp((80+attacker.HIT−target.FLEE)/100, .05, .95)
CRIT = clamp(.01 + .003×LUK, 0, .40)
perfectDodge = clamp(.001×LUK, 0, .10)
damage = max(1, floor(ATK × 100/(100+DEF) × skill × element × critical))
critical = 1.5 on crit, otherwise 1
```

Наприклад: ATK 100 проти DEF 50 = 66; критичний удар = 100; вогонь проти землі = 99 при множнику 1,5 без криту. У цій моделі крити НЕ ігнорують захист та НЕ пропускають перевірку влучання. Навички в MVP гарантовано влучають, звичайні атаки перевіряють HIT. Perfect dodge зараз застосовується до вхідних ударів героїв.

Реалізовані стихії магії: вогонь → земля, земля → вітер, вітер → вода, вода → вогонь: ×1,5; зворотні слабкості ×0,7; інші ×1. Маги в MVP атакують вогняною магією, для ворогів береться `0,8×DEF` як тимчасова магічна стійкість.

Production-розширення:
```text
RangedATK = weaponATK + 2×DEX + floor(STR/5) + Base
variableCast = max(0.2×baseCast, baseCast / (1+DEX/100+INT/200))
MagicDamage = max(1, floor(MATK×100/(100+MDEF)×skill×element))
```
Це проєктні правила, ще не поведінка MVP. Повні таблиці стихій, дебафи, immunity windows, threat і resistances додаються через версійовані effect-configs.

## 7. Інвентар, карти, лут

Кожна істота має гарантований матеріал, Zeny, EXP; шанс зілля 12%; шанс карти `clamp(0.02 + 0.0005×LUK лідера, 0, .05)`. Кап бонусу не дозволяє вивести рідкісний лут за межі 5%. Якщо торба перевантажена, новий предмет не додається; production має направляти його в тимчасове сховище з явним повідомленням.

Спорядження не стекається в production, має UUID. У MVP однакові предмети стекаються, а екіпіровка — шаблон предмета. Карта вставляється у зброю/броню з вільним слотом та споживається; дає +2 ATK/+2 MATK. Карта прив’язана до слота героя, а не окремого екземпляра — це спрощення MVP, production використовує socketed_cards. Зміна спорядження в MVP має заблоковувати або переносити карту явно; перевіряється окремо в коді. Продаж спорядження з карти не реалізований.

У production карти мають специфічні effects: flat_stat, percent_stat, element_override, on_hit_proc, granted_skill. Ефекти обчислюються у визначеному порядку, не виконують довільного JS. Система Merchant: локально 10% знижки першій професії, у production — vending з лімітом слотів і комісією. Відкритий P2P ринок не можна будувати на довірі до localStorage.

## 8. Мобільний UI/UX та wireframe

Палітра: світлий пергамент, темна хвоя, приглушене золото; кольори SP/HP доповнюються текстом. Десктоп: вузька ліва навігація, ігрове поле, права колонка загону/завдань. Portrait: навігація внизу, компактні 6 карток у сітці 3×2 під полем; навички лишаються під полем. Landscape низької висоти: поле + компактна права колонка. Меню — нативний modal dialog із focus trap та Escape; не треба влучати в дрібну іконку на самій карті.

## 9. Серверна версія та безпека

Рекомендована цільова архітектура: той самий статичний клієнт + API/авторизація + авторитетний battle service + PostgreSQL. Бій у окремій кімнаті на 6 героїв; WebSocket snapshots/deltas, server tick 10–20 Hz, client interpolation 60 FPS. Власний загін контролюється намірами, а не присланими значеннями шкоди.

Мінімальний контракт:
- `GET /v1/save` — версійований стан і revision.
- `POST /v1/commands` — operation_id, expected_revision, typed intent.
- `POST /v1/job-advance`, `/v1/stat-allocate`, `/v1/equip`, `/v1/socket` — перевірка прав/ресурсів, транзакція.
- `POST /v1/offline/start`, `/v1/offline/settle` — час сервера, snapshot і rules_version.
- `POST /v1/market/list`, `/v1/market/buy`, `/v1/market/cancel` — escrow та ledger.
- `GET /v1/content?version=...` — незмінний manifest балансу.

Auth — secure HttpOnly cookie; SameSite/CSRF для cookie API, HTTPS, rate limits, сувора схема input. Сервер ніколи не приймає client zeny, час офлайн або результат RNG. Покупка ринку: lock listing + wallets, перевірка seller≠buyer, резерв предмета, списання, зарахування, передача предмета, ledger, idempotent response в ОДНІЙ транзакції. Повторний operation_id повертає попередню відповідь, інший hash на тому ж ключі відхиляється. Для guild/town quests — окремі типи та спільний event processor kill/loot/visit.

## 10. AFK і заряд батареї

MVP: зберегти timestamp; при поверненні обмежити час 4 годинами; обрати дозволених звичайних істот; не більше 240 полювань; за кожне — гарантований матеріал, Zeny й 35% EXP. Без випадкових карт та завершення завдань. Повторний settlement без нового часу нічого не дає. Вкладка не мусить працювати у фоні. Локальний час може бути змінений гравцем; це прийнятно лише для соло-прототипу.

Production: snapshot сили/екіпіровки при відправленні, immutable reward rules, час сервера, idempotent settle та transaction, прогноз перемоги з урахуванням витрат/HP; максимум 4 години. Жодних background loops на телефоні, жодних вимог тримати екран увімкненим.

## 11. Верифікація й наступні етапи

`npm test` перевіряє межі hit/ASPD, монотонність damage/DEF, shortest-path без проходу крізь перешкоди, пороги професій, прогрес, споживання інвентарю, слотування карт і повторне офлайн-нарахування. `npm run check` перевіряє синтаксис модулів. Мобільне та десктопне відображення перевіряється у браузері.

Етапи розвитку: (1) стабілізація соло й балансу; (2) фінальні спрайти/портрети та 5 унікальних карт; (3) повне дерево навичок і AI; (4) серверний save/auth/offline; (5) транзакційний P2P і гільдії. Серверний ринок випускати тільки після тестів конкурентних покупок, дублювання нагород і відновлення після збою.
